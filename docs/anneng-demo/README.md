## 2. 技术结论

建议新项目采用 **React + TypeScript + Vite + Ant Design 6.x + Ant Design X 2.x**。

Ant Design X 负责会话消息、发送框、快捷提问和执行步骤；Ant Design 负责抽屉、表单、状态与工作台布局。文书编辑用 Tiptap，图表用 ECharts，业务状态用 Zustand，真实 Word 输出用 docx。具体官方依据与版本注意事项在 03 文件。

这里推荐的是版本线。Codex 必须在 T-001 核对实际包版本、peerDependencies 和 Node engines，再锁定依赖；本包没有运行 React 依赖安装与应用构建。

P0 只用 AI UI 组件，不接真实模型，不引入额外 Agent Runtime。业务状态由受控 Mock provider 和单一领域 store 管理，不同时维护两套会话状态。

## 3. 本轮真正要做的东西

**一个安小能工作台 + 一个文书工作台。**

主线：灾情摘要 → 查询资源 → 多轮追问 → 选择候选力量 → 查看处置建议 → 生成应急要情 → 缺项补录 → 来源溯源 → 编辑和校核 → 模拟签发 → 导出及本地归档。

应急要情、值班日报完整可用；会议纪要、工作总结只做有明确标记的模板预览。真实多端、语音识别、正式派单、OA、知识库后台和四类完整生成不在本轮 P0。

模型和业务数据可以模拟，但下面这些必须真的实现：资源汇总、上下文联动、编辑保存、规则校核、历史版本、签发门禁、DOCX 文件生成、打印版式、错误恢复及一键重置。

地图采用本地可点击 SVG 空间示意，不调用真实地图服务。PDF P0 使用“打印 / 另存为 PDF”，不是一键下载。应用内版本差异不是 Word 原生 track changes。

## 5. 种子数据使用说明

`scenario.json` 是归一化数据：实体的 `factRefs` 指向 `facts`；事实的 `sourceRecordId + sourceFieldKey` 指向 `sources` 中的原值。`verification=confirmed` 仅表示模拟业务记录的核实状态，不能掩盖 `dataMode=mock`。

所有模拟业务时间独立于真实操作时间。演示时钟初始为 21:10；班次截止时间为次日 00:00，但日报统计截至演示时钟，不把未来时段计入。

三支队伍中两支可用、一支忙碌。主线选择前两支后汇总得到 2 支/64 人/7 台挖掘机；移除第二支后为 1 支/36 人/4 台。`expectedChecks` 只用于测试，不能直接作为 UI 数字来源。

报送单位与交接事项初始为缺失，必须由用户在演示流程中补录并确认。候选力量不是已调派力量；`confirmedDeployments=[]` 不能被解释为现实中无人救援。

`faultScenarios` 是异常操作描述，不是应用初始化时就执行的状态破坏。监测更新新增样本并提升数据版本，不能覆盖已签发文书的来源快照。

## 6. 最容易做错的地方

聊天有变化、右侧永远固定；表面可编辑但导出仍是初始文案；随便改数字仍显示校核通过；只填了 source ID 却不能核对原值；候选被写成已调派；“停止”之后旧任务仍写回；切换事件串数据；刷新一直显示生成中；模拟签发绕过权限或版本；打印后无论是否保存都显示成功。

这些不是可以靠演示话术掩盖的小问题，产品说明和验收用例均将其列为必须验证的行为。

## 7. 文档与应用验收的区别

本包交付的是 Markdown 文档和 JSON 种子，不包含应用源码、模型服务或已完成的浏览器测试。02 中的所有任务默认未完成，截图与测试报告是 Codex 开发后的交付要求。

开发后应提供安装/启动方法、唯一锁文件、测试结果、主要截图、演示脚本与已知限制。不能把“文档写了验收项”当成“应用已经通过验收”。
